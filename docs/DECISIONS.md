# Decision log

| # | Date | Decision | Why | Trade-off / what we tell judges |
|---|---|---|---|---|
| D1 | 22 Nov | Run the model **in the browser** (ONNX Runtime Web, WASM) instead of a FastAPI + TensorFlow server | Organisers require a fully working **local** prototype and want Vercel hosting. TensorFlow CPU is far above Vercel's serverless size limit; a static site with in-browser inference deploys to Vercel as-is and runs locally with one command. The photo never leaves the phone (privacy promise), works offline after first load, no cold starts | The proposal said FastAPI. We changed it for reliability and privacy; the model, data, calibration and tiers are unchanged. Model must stay small: first ≤ 10 MB, later ≤ 30 MB (D8). The shipped file is 16.6 MB |
| D2 | 22 Nov | Train with **PyTorch + timm (`pretrained=False`)** instead of Keras | Reliable ONNX export, easy CAM head, same random-initialisation promise | Proposal said Keras `weights=None`; the scratch-training promise is kept |
| D3 | 22 Nov | TypeScript for the web app | Shared contracts (`Prediction`, `DiseaseCard`) let three people build in parallel without breaking each other | Slightly more typing |
| D4 | 22 Nov | Monorepo `web/` + `ml/`, Vercel root dir `web` | One public repo is a rule; simple to judge | — |
| D5 | 22 Nov | Merge commits only (`--no-ff`), no squash/rebase on shared branches | Rule 10: no squashing or rewritten history; per-member attribution stays visible | Busier history |
| D6 | 22 Nov | Heat-map via CAM (GAP → Linear head) exported as a 2nd ONNX output | Exact, cheap explanation in the browser, no gradients needed | Head design is fixed by this choice |
| D7 | 22 Nov | **Online, train-only augmentation** with `torchvision.transforms.v2` in 3 ablation profiles (`A0_baseline`, `A1_field_realistic`, `A2_field_mixup`); eval reuses `preprocess.py` | Compared 6 research reports. torchvision is BSD and already on Kaggle; original Albumentations is in maintenance mode and AlbumentationsX is AGPL. Reusing `preprocess.py` keeps train/val/ONNX/browser input identical. Bounds protect symptoms: crop ≥ 0.80, hue ≤ ±0.015, blur kernel ≤ 5, erase ≤ 4%, MixUp never mixes Leaf Smut | ~60 lines of our own ops (shadow, down-up, JPEG). The winner is chosen on validation macro-F1 only; BD5 is reported, not tuned on |
| D8 | 22 Nov | Model size limit raised from 10 MB to **30 MB** ONNX (shipped: 16.6 MB, FP16-stored weights, FP32 maths) | Shadow chose maximum scratch accuracy over download size; ONNX Runtime Web, Vercel and GitHub serve 30 MB fine. CI gate in `web/src/deploy/deploy.test.ts` | First load is slower on rural mobile data; the file is cached after that |
| D9 | 22 Nov | Train on a **unified build of four public Bangladeshi rice datasets** (RiceLeafDiseaseBD v3 + BanglaRiceLeaf + RiceLeafBD real-field; BD5 kept as an external test) instead of RiceLeafDiseaseBD v3 alone | One district / one season / two phones was the proposal's own biggest risk (§11). More sources give more variety of fields, phones and light. Same 6 classes, same stratified 70/15/15 with a fixed seed, near-duplicates (perceptual hash) kept in one split, test used once | The numbers are not directly comparable with papers that use v3 alone. All sources are CC BY 4.0 / CC0 and credited in `docs/CREDITS.md` |
| D10 | 22 Nov | Ship a **per-class blend of MobileNetV3-Large-CAM + RegNetY-400MF** (both random init) instead of one MobileNetV3-Small | The proposal said the choice would be made by validation macro-F1 and size, not in advance. We trained three scratch candidates (P1/P2/P3, `ml/kaggle/top3/`); P2+P3 had the best validation macro-F1 at 16.6 MB, under the 30 MB limit (D8) | Larger and slower than MobileNetV3-Small. Still scratch-trained, still one ONNX file, still runs on a phone browser |
| D11 | 22 Nov | **Not-rice gate (M3)** in the same ONNX graph: a small scratch CNN trained with PlantDoc + COCO negatives | The proposal listed "no not-rice class" as a risk and put it on the roadmap. We pulled it forward so a photo of grass, another crop or a random object gets "this is not a rice leaf" instead of a disease name | About 1 in 4 other-crop leaves still pass (see MODEL_REPORT) |
| D12 | 22–23 Nov | **Roadmap items pulled forward** into the web MVP: offline use (PWA), Bangla audio (Web Speech + pre-generated MP3), not-rice gate (D11), scan history, heat-map | Each was cheap once inference ran in the browser (D1), and each helps farmers with weak internet or low literacy | Android app, INT8 and field trials stay on the roadmap |
| D13 | 22 Nov | **Scan history (F9) keeps a small thumbnail (≤ 200 KB) on the user's own device only** (IndexedDB) | Lets a farmer show past scans to an officer. This refines the proposal's "images are not stored": nothing is ever sent to or stored on any server; the history lives only in that phone's browser and can be cleared at any time from the History screen | Anyone with the phone can see the history; the user can delete it |
| D14 | 23 Nov | **Weather disease risk (F16) uses division dropdown only, no GPS** | Privacy guardrail strictly prohibits geolocation or GPS tracking. Farmers pick one of 8 divisions from a dropdown; only that division's fixed headquarters coordinate is queried from Open-Meteo. The choice is stored in localStorage on the device only. If anyone adds a Content-Security-Policy (CSP) later, it must include `connect-src 'self' https://api.open-meteo.com`. | Division-level headquarters coordinate (coarser than GPS), but preserves complete user privacy and works offline via cache. |
| D15 | 23 Nov | **F16 v2: optional GPS on the Weather tab only (supersedes the no-GPS part of D14)** | Leaf scanning uses no location; the Weather tab asks for browser location only when opened, rounds it to 2 decimals (~1 km), sends it only to Open-Meteo, stores it only in the browser; the division dropdown stays as fallback; the per-disease bands are heuristic, not validated, and tungro is not weather-scored. | Opt-in coarse GPS (~1 km) gives accurate local forecasts without revealing precise homestead coordinates; scanning remains 100% zero-location. |
| D16 | 23 Nov | **Weather tab shows the area name for the GPS point ("মিরপুর, ঢাকা")** | On "অটো লোকেশন", the same rounded point (2 decimals, ~1 km) is also sent to OpenStreetMap Nominatim reverse geocoding (one request per tap) to show the area/sub-district/district name and to label the crop-rotation card. Nothing is stored server-side; the name is cached only in the browser with the forecast. Offline or on failure it falls back to the nearest division. Credit: © OpenStreetMap contributors. Leaf scanning still uses no location. If a CSP is added later it must also allow `connect-src https://nominatim.openstreetmap.org`. | Farmers see their own area name, at the cost of a second third-party request for the coarse point. |
| D17 | 23 Nov | **Screen-recapture fine-tune not shipped**; the live model stays `v2-blend-p2-p3-scratch-gate` (macro-F1 0.894) | A P2/P3 fine-tune on simulated screen photos raised screen-photo macro-F1 to 0.804 but dropped clean internal test to 0.888, below our own rule (ship only if clean test ≥ 0.890) | Photos of a laptop/phone screen stay weak (≈ 0.65); we say so openly and the tiers and "not sure" protect the user |
| D18 | 23 Nov | **Weather tab: division dropdown removed** (#50); a location pill beside "Auto Location" shows the GPS area name; Dhaka is the fallback when location is denied or fails (supersedes the dropdown fallback in D14/D15) | One tap is simpler for farmers than picking a division; the pill shows the D16 area name in the current language | Without location permission a farmer outside Dhaka sees Dhaka's weather; the screen says so and asks them to turn location on |
